## 3. The Architecture Mismatch Explained

| Dimension | Live GitHub Repository Settings | Hardened Architecture in PR #16 |
| :--- | :--- | :--- |
| **Build Type** | `legacy` ("Deploy from a branch") | GitHub Actions (`actions/deploy-pages@v4`) |
| **Publishing Source** | Branch `main`, Path `/` (Repository Root) | `public-site/` directory generated by `build_public_site.py` |
| **Security Allowlist** | Ignored by GitHub Pages (serves root files) | Enforced by `scripts/build_public_site.py` |
| **Deployment Trigger** | Automatic on push to `main` via Jekyll/HTML engine | Orchestrated by `.github/workflows/deploy-pages.yml` |

### Why This Is a Critical Release Gate Blocker
Under the current `legacy` configuration:
1. If PR #16 is merged into `main`, GitHub Pages will immediately trigger an automated build that serves the root directory (`/`) of `main`.
2. The hardened `public-site/` staging directory generated by `build_public_site.py` would be completely bypassed.
3. Although legacy diagnostic reports have now been untracked from Git, serving directly from repository root exposes non-production files (e.g. `.github/`, unit test files, internal scripts) to potential path routing.
4. The GitHub Actions deployment job (`Deploy to GitHub Pages` via `actions/deploy-pages@v4`) cannot publish pages while `build_type` is set to `legacy`.
